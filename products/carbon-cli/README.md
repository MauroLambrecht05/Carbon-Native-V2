# carbon-cli

The `carbon` command: scaffold, build, run, bundle and publish carbon apps.

```sh
bazel run //products/carbon-cli:carbon -- --help     # through Bazel
bun products/carbon-cli/main.ts --help               # or directly
```

Both do the same work. See `.tools/orchestration/bazel/bun/README.md` for what
the Bazel wrapper does and does not guarantee.

The CLI runs on **Bun, not Node**: the bundler drives `Bun.build`,
`doctor.command.ts` imports `spawnSync` from `"bun"`, and workspace resolution
detects Bun's compiled-binary VFS. Under `node` the entrypoint loads and then
dies at the first Bun import.

## Layout

Follows the common product template — see [`../README.md`](../README.md).

```
products/carbon-cli/
├── main.ts                    builds the Dispatcher, runs it, exits
├── composition/
│   └── registry.ts            every command, declared lazily
├── presentation/
│   ├── framework/             Command · Dispatcher · Registry · Flags · Help · Io
│   └── commands/
│       ├── project/           init · create
│       ├── build/             build · run · dev · bundle
│       ├── release/           signer · publish
│       ├── plugins/           plugin
│       └── diagnostics/       doctor
└── tests/
    └── registry.test.ts       the assembled command set is coherent
```

There is no `domain/` or `application/` here, by rule. Everything these
commands *do* — building, signing, packaging, updating — is
`@carbon/toolchain`. The product turns argv into a use-case call and an exit
code, and nothing else.

## Commands

| Command | What it does |
|---|---|
| `init` (`new`) | Scaffold a new project |
| `run` | Build whatever needs building, then launch |
| `build` | Build UI + shell + runtime, don't launch |
| `dev` | Watch sources, rebuild and relaunch on save |
| `plugin` | Manage native plugins (new / build / install / list / info) |
| `signer` | Ed25519 signing and key management |
| `bundle` | Create OS-specific installers |
| `publish` | Manage releases and delta updates |
| `doctor` | Check toolchain dependencies |

## Adding a command

1. Write a class extending `Command` (or `CommandGroup`) under
   `presentation/commands/<area>/`.
2. Add one `defineCommand(...)` entry to `composition/registry.ts`.

Nothing else. Help, aliases, per-command `--help`, typo suggestions and
exit-code handling all come from the metadata. V1 needed four edits — a switch
in `main.ts`, a hand-maintained `HELP` template, the command file, and a help
block inside it — and the template drifted from the switch more than once.

### Why the metadata is declared twice

`composition/registry.ts` repeats each command's name and summary rather than
importing the class to read them. That is what keeps `carbon --help` from
loading vite, rollup and babel: a descriptor is metadata plus a `load()` thunk,
and only the matched command is ever imported. Measured, the bundler alone
costs ~68 ms to evaluate.

The duplication is guarded — `tests/registry.test.ts` loads every command and
fails if a descriptor and its class disagree.

## Signing

`carbon signer` calls `@carbon/toolchain` in process. V1 shelled out to
`${VENDOR_DIR}/carbon-signer`, a binary nothing in the repository built, so
every subcommand failed with ENOENT on a clean checkout.

Key files stay byte-compatible with V1's format: Argon2id (m=65540, t=3, p=4)
over XChaCha20-Poly1305, Ed25519 signatures, minisign-style `.pub`/`.key`/`.sig`
layout. Keys generated by V1's Rust crate open here and vice versa. Crypto is
`@noble/*` — pure TypeScript, no native module, no per-platform binary.

```sh
carbon signer generate --name myapp
carbon signer sign bundle.bin --key myapp.key      # writes bundle.bin.sig
carbon signer verify bundle.bin --pubkey myapp.pub
carbon signer rotate --key myapp.key               # cross-signed keyring
```

Password resolution: `--password`, then `$CARBON_SIGNER_PASSWORD`, then an
interactive prompt. A non-interactive run with no password fails rather than
hanging on a stdin that will never produce anything.

> `signer rotate` writes the new keypair under the old key's basename, so
> `--out` pointing at the key's own directory overwrites the outgoing secret
> key — which you still need for the validity window. Inherited from V1.

## The release binary

```sh
bazel run //products/carbon-cli:compile      # -> dist/carbon.exe, ~118 MB
```

Bundles the CLI and the Bun runtime, so it runs where Bun is not installed.
That is its only advantage: it starts ~250 ms slower than `bun main.ts`, so it
is a distribution artifact, not a dev-loop step.

Copy it anywhere and it keeps working — the workspace root is found by
searching upward for `MODULE.bazel`, first from the executable, then from the
current directory. `CARBON_ROOT` overrides the search. (The search replaced
level-counting, which broke the moment the binary left `dist/`.)

## What does not work yet

Blocked on V2 migration phases 3–5, not on the CLI:

- **`build` / `run` / `dev`** compile a Rust runtime that has not been migrated.
  `WorkspaceLayout` points `RUNTIME_DIR` at `solutions/internal/runtime`, which
  does not exist yet.
- **The build pipeline** imports `@carbon/mini-solid` and `@carbon/compat-dom`
  — the Solid renderer and the DOM-compat shim, both unmigrated.
- **`publish`** is a placeholder in V1 too: it emits `signature_placeholder`
  and `sha256_placeholder`.
- **`init`** scaffolds correctly but its `bun install` fails — the template
  pins `@carbon/mini-solid` to a `packages/` directory that has not existed
  since V1.
- **`bundle`** never invokes an installer. `@carbon/toolchain`'s
  `infrastructure/packaging/` generators are dead code.

Verified working: `--help`, `doctor`, and `signer` (all four subcommands,
including wrong-password and tampered-payload rejection).
