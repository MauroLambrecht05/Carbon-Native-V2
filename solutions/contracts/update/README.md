# update

What a release announces to an installed app: version, channel, rollout
percentage, keyring and per-platform artifacts.

**Agreement** `types/UpdateManifest.ts`
**Honoured by** `capabilities/distribution/signing` (writes and signs it) and
`capabilities/distribution/updating` (fetches and verifies it)

This subject exists because those two capabilities had the same struct
duplicated, each with its own copy — exactly the drift a contract prevents.

Types only for now. When the wire form is pinned it gains `schema/update.fbs`
and switches to `flatbuffers_subject`; today the manifest is JSON, and the
signature covers its exact bytes, so the canonical serialization in
`SignManifestUseCase` is part of the agreement.

## Conformance

`fixtures/conformance.json` holds the cases every consumer of a manifest must
agree on: signature bytes, version ordering, the rollout bucket, the stop list,
compatibility, and channel movement. It is generated by
`.tools/automation/contracts/generate-update-conformance.ts` from the
publisher's own manifest builder and serializer, signed with a fixed test key.
Do not edit it by hand; `--check` fails when it is stale.

It is run by:

- the TypeScript updater, `capabilities/distribution/updating/tests/conformance.test.ts`
- the Rust updater packaged apps use, `capabilities/distribution/updating/rust/application/decide.rs`
- the standalone updater, `products/carbon-updater/tests/update-checker.test.ts`
