# Platform contract v1

Carbon Cloud owns account, organization and canonical catalog identity. Carbon
Database and Carbon Registry independently own and authorize their resources.
This subject contains their shared wire agreements, not browser page models.

`schema/platform.schema.json` is JSON Schema 2020-12. `types/Platform.ts` is
generated by `.tools/automation/contracts/generate-platform-types.ts`.
`parseComponent` validates unknown data with Ajv without coercion, defaults or
removal of unknown properties. Validation errors never echo submitted values.
Use type-only imports in a browser when runtime validation is unnecessary.

The dependency pins follow the maintainers' current
[Ajv releases](https://github.com/ajv-validator/ajv/releases) and
[jose releases](https://github.com/panva/jose/releases). Ajv is also overridden
for ajv-formats so both use the same patched validator implementation.

## Compatibility

- Route major: `/platform/v1`, `/internal/platform/v1`, and the owner-specific v1
  routes documented in the backend plan. JSON responses use `application/json`;
  event payloads carry `version: 1`. No unversioned alternate write authority.
- UUIDs are opaque. Revisions and sequences are decimal strings. Exact amounts
  are normalized decimal strings: no exponent, leading zeroes, trailing fractional
  zeroes or negative zero. Times are RFC 3339 UTC with `Z`.
- New optional fields are additive only when the receiving old version already
  accepts them. These components deliberately reject unknown properties, so
  senders must negotiate such additions or continue emitting the older shape.
  Unknown enum members and new required fields are breaking changes.
- Breaking changes require a new major and an explicit N/N-1 deployment window.
  Keep old schemas and fixtures during that window. Do not edit an already
  deployed contract incompatibly. v1 is currently under implementation and has
  not passed the production cutover gate.
- Deprecation must publish a sunset date and consumer migration evidence. There
  is no implicit sunset for existing `/v1` consumers in this change.

## Requests and errors

Every request has a UUID `X-Request-Id`. Retryable commands require an
`Idempotency-Key` scoped to actor, operation and resource; state-dependent changes
also require `If-Match` or `expectedRevision`. An asynchronous commit returns 202
and `OperationReceipt`; a synchronously committed new resource returns 201.
Idempotency is separate from assertion replay: each HTTP attempt uses a fresh
assertion while retaining the command key. Persisted receipts must never contain
creation-only credential values.

Error categories are `unauthenticated` (401), `forbidden` (403), `not_found`
(404), `conflict` (409), `validation` (400), `capability` (501), `quota` (429),
`rate_limited` (429), `unavailable` (503), and `internal` (500). Inaccessible
foreign resources return 404. Errors carry safe messages and request IDs.
Browser adapters explicitly translate the older mock error names; they must not
change behavior by catching a network failure and substituting mock state.

Pages have bounded items and an opaque nullable next cursor. Totals are optional
because expensive/visibility-sensitive counts cannot always be returned. Cursors
must bind visibility revision, resource scope, filters and sort. This schema does
not implement pagination authorization; the owning capability must enforce it.

## Service assertions

The identity capability signs EdDSA assertions with a pinned issuer, audience,
key ID, explicit `carbon-internal+jwt` type and a maximum 60-second lifetime.
The signed request includes exact method, pathname/query and SHA-256 body digest.
Recipients validate the expected principal kind, exact resource scope and grant,
recheck live authority and atomically consume `jti` in their own Postgres replay
table. Retain replay IDs until expiry plus the five-second clock tolerance.
Caller-supplied key-discovery headers are rejected; rotation uses locally pinned
overlapping keys. No browser cookie is an internal assertion.

These choices follow [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html).
The verifier is a building block; independent product endpoints and the live
Cloud authority protocol still need wiring before this boundary is enabled.

## Redaction and events

`x-carbon-sensitive` and `x-carbon-disclosure: creation-only` annotate secrets.
Credentials must not be copied into audit, event, error or operation projections.
Those schemas reject arbitrary metadata and customer payloads; `SafeMetadata`
only permits named, bounded fields. Do not log unvalidated input.

Operations include partial success and immutable terminal states. Events are
persisted in the owning transaction before publication, use exact sequences,
and contain resource references instead of customer rows. Stream consumers
deduplicate event IDs and process `authorization_revoked` as terminal.
State transitions and stream delivery belong to capabilities, not this schema.

## Verification

```sh
bun .tools/automation/contracts/generate-platform-types.ts --check
bun test solutions/contracts/platform/tests
bun test solutions/capabilities/cloud/identity/tests
bazel test //solutions/contracts/platform:conformance_test
bazel test //.tools/automation/contracts:platform_types_test
```

`fixtures/conformance.ts` supplies one typed fixture for every component. The
tests reject token confusion, invalid scope hierarchies, unsafe projections,
noncanonical decimals and invalid timestamps. Per-feature endpoint OpenAPI and
cross-product runtime conformance are added with their implementations; these
common components alone do not prove platform parity.
